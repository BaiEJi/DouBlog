EXPLAIN中，列表由单列created索引扫描加临时排序，变为联合索引搜索，无临时排序；COUNT变为覆盖索引搜索。不是通过删除正文或减少返回行数提速。源数据库/WAL状态、相关源码、工具结束指纹均不变。

## 公共HTTP路径静态复核

普通有效Cookie请求与基线一样，只进行一次会话HMAC验证，不经过账号SQL或认证SDK池；访问日志和gzip参数也与基线一致。每个`run_db`调用仍只提交一次SDK任务、包装一次Future；两类票据覆盖不同生命周期，显式runtime绑定和queued-cancel完成回调均有必要，没有发现重复SQL/序列化/Session构造。

`run_blocking`与SDK的默认行为确有两次context复制，但常规Cookie读请求走`run_db`，不进入这条路径。缺少对应耗时证据，也无法解释本轮暖缓存/轻SQL场景的负值，故不继续修改公共并发机制。该复核仅为静态调用证据，不是额外CPU采样或性能豁免。

## 交付审计：惰性资源登记与测试调度

静态审计发现Confcenter只导出停止钩子，而公共启动登记此前只接收有启动钩子的模块，导致它的Redis/缓存/限流清理未进入退出和切库路径。新增真实lifespan测试在原cbcc源码上复现关闭次数0而非1；公共登记已支持仅有stop钩子的惰性资源，启动成功后才登记，停止失败保留供重试。新增6项及相邻23项均通过，覆盖重入、关闭一次、切库、独立app及失败重试。原cbcc固定CPU完整轮因此在仅4场景时中止，`http-affinity-complete-cbcc.aborted.json`明确标为不可用于验收；不能将其部分数据称为完整轮。

修复版首次全量为929通过、1失败，失败在书签并发迁移测试的栅栏处，迁移SQL尚未执行。`sdk_lazy_scale_diagnostic.json`通过仅控制诊断池的首次出队窗口，复现SDK在第二次submit时看到spawned=1/idle=1/queued=1，未扩容第二worker；首任务若等待队列中的第二任务便会超时。SDK实际submit/扩容代码未改，两个诊断任务均正常释放并结束，SDK文件SHA未变。
